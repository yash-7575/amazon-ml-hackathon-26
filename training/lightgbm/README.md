# LightGBM Entity Matching Pipeline

**Stage-2 matcher** for the Amazon ML Challenge 2026 Business Entity Resolution task.

This module takes `candidate_pairs.tsv` generated by the blocking pipeline (`blocking/`) and trains a LightGBM binary classifier to predict `P(match)` for each candidate pair. It implements the full training, evaluation, and prediction pipeline with proper leakage prevention, class imbalance handling, and competition-metric optimization.

---

## 1. Why LightGBM?

- **Gradient boosting on tabular features** is the established SOTA for entity resolution (ER) with hand-crafted features — see *Christen ch.5*, *Splink*, *dedupe*, *epfl-dlab/entity-matchers* re-evaluation.
- **Native missing-value handling** (NaN = "missing", not "zero similarity") — critical for address fields where 3.3% are empty (FINDING 7).
- **Fast training & inference** with `scale_pos_weight` for ~1:6 pair-level imbalance.
- **Deterministic** with `seed` and `force_col_wise`.
- **Feature importance** (gain/split) for interpretability and ablation.
- **Reusable feature/evaluation code** for future XGBoost experiment (same data, same split, same metrics).

## 2. Pipeline Position

```
RAW S1/S2/S3
    ↓
normalization (blocking/normalize.py — Unicode category strip, suffix drop)
    ↓
country partition (blocking/ — FINDING 2: 0 cross-country matches)
    ↓
candidate generation (blocking/blocker_v1.py — P1 exact + P2 name TF-IDF + P3 addr TF-IDF + P4 translit)
    ↓
candidate_pairs.tsv  ←── INPUT TO THIS MODULE
    ↓
pairwise features (this module: features.py)
    ↓
LightGBM binary classifier (this module: train.py)
    ↓
P(match) per candidate pair
    ↓
threshold tuned on macro-F0.5 (this module: evaluate.py)
    ↓
final matching + one-to-one assignment (future: global DSU + Hungarian/greedy)
    ↓
matching_results.tsv (submission format)
```

## 4. Label Generation

Labels are created by **exact join** of candidate pairs against ground truth:

```python
true_pairs = set(zip(gt['source1_entity_id'], gt['matched_entity_id']))
label = 1 if (s1_id, cand_id) in true_pairs else 0
```

- **Positive** = true entity match (in ground truth)
- **Negative** = candidate proposed by blocker but not in ground truth (hard negatives!)
- **Ground truth is NEVER used as a feature** — only for labels and evaluation.

| Feature | Description |

|---------|-------------|

## 6. Leakage Prevention

| Check | Implementation |
|-------|----------------|
| **Train/val split by S1 entity** | All candidates for a given S1 go to either train OR val, never both (`split_by_s1_entity`) |
| **No ground truth in features** | Features computed only from name/address/country; `label` column excluded |
| **No target encoding** | No feature uses label statistics |
| **Frozen blocker config** | `final_top_k=150` fixed; group-relative features stable |
| **Leakage audit** | `utils.check_leakage()` reports S1/candidate/pair overlap |

---

## 7. Class Imbalance Handling

Pair-level imbalance ≈ **1:6** (positive:negative).

- **Primary:** LightGBM native `scale_pos_weight = neg/pos` (set automatically from training data)
- **No oversampling/SMOTE** — unnecessary for tree ensembles with proper weighting
- **Metric:** PR-AUC (not ROC-AUC) for threshold selection — correct for imbalance (Saito & Rehmsmeier)

## 9. Evaluation (`evaluate.py`)

```bash
PYTHONPATH=. python training/lightgbm/evaluate.py \
    --model training/lightgbm/outputs/models/lightgbm_model.pkl \
    --candidates blocking/candidate_pairs.tsv
```

### Competition Metric: Macro-Averaged F0.5

**Per S1 entity:**
```
P = TP / (TP + FP)          (1.0 if TP+FP=0)
R = TP / (TP + FN)          (1.0 if TP+FN=0)
F0.5 = (1.25 * P * R) / (0.25 * P + R)   (1.0 if both empty)
```

**Final score:** Mean of F0.5 across **all S1 entities** (including singletons).

> **Why per-entity?** FINDING 1: matching is one-to-one. 5.58% of S1 entities are singletons — predicting empty scores 1.0 ("free points"). Under-predicting beats over-predicting (F0.5: 0.833 vs 0.714 for 1-of-2 with 1 FP).

### Additional Metrics

| Metric | Description |
|--------|-------------|
| Macro Precision / Recall / F1 | Per-entity averages |
| Global Precision / Recall / F1 | Micro-averaged over all pairs |
| PR-AUC / ROC-AUC | Pair-level ranking quality |
| Top-K Accuracy | For each S1, is any true match in top-K by probability? |
| MRR / NDCG@5 / NDCG@10 | Ranking metrics |
| Confusion Matrix | TP/FP/FN/TN |
| Singleton Analysis | Separate F0.5 for singleton vs non-singleton entities |

## 10. Threshold Optimization

**Never use 0.5 blindly.** We sweep thresholds and select on **validation macro-F0.5**:

```
Thresholds: 0.10, 0.15, 0.20, 0.25, 0.30, 0.35, 0.40, 0.45, 0.50,
            0.55, 0.60, 0.65, 0.70, 0.75, 0.80, 0.85, 0.90
```

For each: macro-F0.5, precision, recall, F1, n_predicted.

**Best threshold saved** and used for final predictions. Never selected on test/holdout.

---

## 11. Entity-Level Evaluation

Evaluation is **always per S1 entity**, then averaged (macro). The `metrics.macro_f05_per_entity()` function:

1. Groups predictions by `s1_entity_id`
2. Computes TP/FP/FN per entity
3. Calculates F0.5 per entity (singletons → 1.0 if correct)
4. Averages across all entities

### Error Analysis

`metrics.error_analysis()` produces a DataFrame with:
- False positives (high prob, not in ground truth)
- False negatives (low prob, in ground truth)
- True positives
- Sorted by entity and error type for manual inspection

## 12. One-to-One Assignment (Future / Stage 3)

**Current LightGBM experiment:** Evaluates raw thresholded predictions (independent binary decisions).

**Production pipeline** (per PROJECT_CONTEXT Architecture §2.5):
1. LightGBM → `P(match)` per candidate pair
2. Build candidate graph (S1–S2/S3 edges weighted by P(match))
3. DSU to find connected components
4. Small components → exact Hungarian assignment (optimal)
5. Giant component → greedy by descending score (near-optimal)
6. Threshold tuned on macro-F0.5

> **For this experiment:** We report both (A) raw thresholded and (B) note that global assignment is the next step. Do not mix the two evaluations.

## 17. Assumptions & Known Limitations

1. **Candidate TSV exists** — blocking pipeline must have run first (`python -m blocking.blocker_v1 --split train`)
2. **Test data has France** — country partitioning handles open set (no hard-coded country list)
3. **Phone extraction is heuristic** — address field may contain phone numbers; patterns cover US/intl
4. **City extraction is approximate** — no geocoding/external data (competition rule)
5. **is_mutual_best placeholder** — requires full bipartite index; currently 0.0
6. **No TF-IDF cosine features yet** — would require fitting vectorizers on train only (future)
7. **Address parsing is heuristic** — postal code/house number regexes cover common patterns
