# XGBoost Entity Matching — Stage 2 Pipeline

## Overview

This folder contains a complete XGBoost-based Stage-2 entity matching pipeline for the Amazon ML Challenge 2026 Business Entity Resolution task.

The pipeline takes candidate pairs generated by the existing blocking/candidate-generation stage (`blocking/candidate_pairs.tsv`), computes pairwise features, trains an XGBoost binary classifier, optimizes the decision threshold on macro-averaged F0.5, and produces detailed evaluation reports.

## Pipeline Position

```
RAW DATA
    ↓
Normalization (blocking/normalize.py)
    ↓
Country Partition
    ↓
Candidate Generation (blocking/blocker_v1.py)
    ↓
candidate_pairs.tsv  ←────────── INPUT TO THIS PIPELINE
    ↓
Pairwise Features (this pipeline: features.py)
    ↓
XGBoost Binary Classifier (this pipeline: train.py)
    ↓
P(match) probabilities
    ↓
Threshold Optimization (macro-F0.5)
    ↓
Entity-Level Evaluation (macro-F0.5 per S1 entity)
    ↓
Reports & Predictions
```

## Label Generation

Labels are created by joining candidate pairs with ground truth:

- **Label = 1** if `(s1_entity_id, cand_entity_id)` exists in ground truth
- **Label = 0** otherwise

Ground truth is **never** used as a feature — only for training labels and evaluation.

## Feature Engineering

The pipeline computes ~40+ pairwise features derived ONLY from the four input columns:
`entity_id`, `business_name`, `business_address`, `country`

### Name Features
- Normalized exact match (full name & core name)
- Jaro / Jaro-Winkler similarity
- Levenshtein/edit similarity
- Token Jaccard / Dice (with & without suffix stripping)
- Token set ratio / Token sort ratio
- Character 3-gram & 4-gram Jaccard
- Asymmetric containment (S1 in cand, cand in S1)
- Digit conflict detection (e.g., "Store 14" vs "Store 15")

### Address Features
- Normalized exact match
- Token Jaccard / Dice (with & without stopwords)
- Character 3-gram Jaccard
- Levenshtein similarity
- City match (heuristic extraction)
- Postal code match (US ZIP, India PIN, UK postcode)
- House/building number match (leading digits)
- Asymmetric containment

### Phone Features (extracted from address field)
- Exact match
- Normalized (digits-only) match
- Suffix match (last 7 / 10 digits)
- Missing phone indicators

### Cross-Script Features
- Cross-script indicator (ASCII vs Devanagari)
- Transliteration similarity (Devanagari → Latin via ITRANS/unidecode)

### Group-Relative Features (per S1 entity's candidate group)
- Rank within group (by blocker score)
- Is top-1 candidate
- Score margin to 2nd best
- Score ratio to max
- Group size (number of candidates)
- Number of competitors (within 10% of top score)
- Mutual best indicator (placeholder)

### Cross-Field Features
- `name_high_addr_low`: High name sim (>0.7), low addr sim (<0.3) — generic name collision signal
- `name_low_addr_high`: Low name sim (<0.3), high addr sim (>0.5) — address-only match signal (FINDING 3)
- `sim_disagreement`: |name_sim - addr_sim|

### Missingness Indicators
- Address missing (S1, candidate, either, both)
- Length differences (name, address)
- Token count differences

**Important**: Missing similarities encoded as `NaN` (not 0) — XGBoost handles NaN natively. This follows PROJECT_CONTEXT Finding 8: ~3.3% of S2/S3 have empty address.

### Features Explicitly Excluded (Leakage Prevention)
- `country_match` — constant within country partition (Finding 10)
- Any feature derived from ground truth labels

## Train/Validation Split

**Group-aware split by S1 entity** — all candidate pairs for a given S1 entity go to either train OR validation, never both.

This prevents the model from memorizing entity-specific patterns and ensures no leakage between splits.

Split ratio: 85% train / 15% validation (configurable)
Seed: 20260926 (configurable)

## Class Imbalance

Candidate pairs are heavily imbalanced (~1:6 positive:negative).

Strategy: XGBoost native `scale_pos_weight = negative_count / positive_count`

No SMOTE or oversampling — tree-based models handle imbalance well with proper weighting.

## Primary Metric: Macro-Averaged F0.5

The competition metric is **macro-averaged F0.5 per S1 entity**:

For each S1 entity:
```
F0.5 = (1.25 × Precision × Recall) / (0.25 × Precision + Recall)
```

Then average F0.5 across ALL S1 entities (including singletons).

**Key properties:**
- Precision weighted 2× recall
- Correct empty prediction on singleton = 1.0 F0.5 (free points)
- Over-predicting penalized more than under-predicting

**Do NOT compute F0.5 from global precision/recall** — must be per-entity then averaged.

## Threshold Optimization

Threshold is NOT fixed at 0.5.

Evaluated grid: `[0.10, 0.15, 0.20, 0.25, 0.30, 0.35, 0.40, 0.45, 0.50, 0.55, 0.60, 0.65, 0.70, 0.75, 0.80, 0.85, 0.90]`

Selected threshold = argmax(validation macro-F0.5)

Saved to: `outputs/metrics/best_threshold.json`

## Entity-Level Evaluation

For every S1 entity, the pipeline computes:
- True matches, candidate count
- Predicted matches (after threshold)
- Top-1 / Top-K accuracy
- Per-entity Precision, Recall, F0.5
- Error categorization (generic name collision, address-only match, cross-script, etc.)

## Leakage Audit

The pipeline includes an automated leakage audit (`leakage_audit.md`) that checks every feature for:
- Target label references
- Ground truth keywords
- Validation/test set references
- Global statistics that might encode label information

All features are documented with risk level (NONE/LOW/MEDIUM/HIGH) and decision (KEEP/REVIEW/DROP).

## Error Analysis

Detailed error analysis identifies:

**False Positives:**
- Generic name collisions (e.g., "Primary Care Group" in multiple cities)
- Ambiguous both-high (name & address both similar but different entity)
- Cross-script mismatches
- Phone / postal code mismatches
- Digit conflicts ("Store 14" vs "Store 15")

**False Negatives:**
- Address-only matches (no name overlap — FINDING 3)
- Cross-script true matches
- Low-confidence true matches
- Name variations (abbreviations, transliterations)

## One-to-One Matching

The underlying problem is one-to-one (PROJECT_CONTEXT Finding 1: 7.6M matched slots, 7.6M distinct IDs, zero reuse).

This pipeline outputs **per-pair P(match) probabilities**.

Global one-to-one assignment (DSU components → exact/greedy assignment) is a subsequent stage. The raw binary classifier metrics are reported separately from any assignment-stage metrics.

## Comparison with LightGBM

This XGBoost pipeline is designed for **direct comparison** with the LightGBM experiment (`training/lightgbm/`):

- Same candidate pairs (`candidate_pairs.tsv`)
- Same ground truth
- Same train/validation split (group-aware by S1 entity)
- Same feature set (reuse `features.py` logic)
- Same evaluation code (reuse `metrics.py`)
- Same threshold search procedure
- Same macro-F0.5 per S1 entity calculation

When both experiments exist, results can be compared in `outputs/reports/lightgbm_vs_xgboost.md`.

## Key Design Decisions

1. **No ground truth in features** — Enforced by design
2. **Group-aware split** — Prevents S1 entity leakage
3. **NaN for missing** — Not 0, following Finding 8
4. **Macro-F0.5 per entity** — Not global F0.5
5. **Threshold on validation** — Never on test/holdout
6. **Feature parity with LightGBM** — Same features for fair comparison
7. **Windows-compatible paths** — Uses raw strings for Windows paths

## Troubleshooting

**Memory issues:** The feature matrix can be large. If OOM:
- Reduce `final_top_k` in blocking config (fewer candidates per S1)
- Process in chunks (not yet implemented for full dataset)
- Use `dtype=float32` (already default)

**Slow feature computation:** The loop in `compute_features` is single-threaded. For full dataset, consider:
- Multiprocessing (not yet implemented)
- Pre-computed feature cache

**Missing dependencies:** Ensure `rapidfuzz` and `xgboost` are installed. On Windows, `xgboost` may require Visual C++ redistributable.
